# Companion UI Polish Direction

> 2026-09-26 Owner 真实试用后的后续设计输入。此文只记录方向，不代表已定稿或要求在 COMPANION-003 / 004 内实现。

## 已确认的问题

- 当前 Companion 页面仍有明显“AI 工具 / 工程调试台”气质，不够像长期日常使用的陪伴应用。
- 常驻说明文字、状态说明和技术术语过多，视觉密度偏高；多数解释应删除、弱化或只在需要时出现。
- 语音不应作为输入框之外的一排独立控制按钮；主入口应与 Composer 融合。
- 功能状态不应靠大量按钮暴露。正常语音路径应尽量只有一个主操作：开始说话 → 说完 → 自动识别 → 自动提交 → 自动播放。
- 设置、异常恢复、播放重试、停止声音等次级能力只在对应状态下按需出现。
- Live2D 待资源状态不应在普通页面抢占主要视觉层级。

## 后续设计方法

1. **先做视觉参考，不直接让工程实现自由发挥。**
2. 使用 GPT Image 先生成 2～4 张 Companion 桌面 UI 参考稿，重点探索：
   - 极简陪伴感；
   - 主流聊天应用式输入区；
   - 更柔和的“小窝 / 日常陪伴”方向。
3. Owner 先挑选 / 组合认可的视觉方向，再把选定图片作为 implementation 的主要视觉参照。
4. 工程实现按参考稿收敛，不在实现阶段自行堆叠说明文字、状态标签或“看起来像 AI Demo”的组件。

## 当前偏好的交互原则

- Composer 是页面核心：文字输入、语音入口、发送操作尽量整合在同一区域。
- 语音入口优先放入输入框内部或紧邻发送按钮，而不是独立占一整行。
- 普通状态不展示技术实现词，如 provider / readiness / candidate / implemented 等。
- 页面只保留用户此刻需要知道的内容；技术证据留在日志、测试、设置详情或开发入口。
- 视觉上优先留白、层级和一致性，不靠“多写几句解释”弥补交互设计。
- 后续 Polish 不改变已建立的文字 / 语音 / Memory / Thinking / Live2D / Engineering 边界，只做产品层交互与视觉收敛。
