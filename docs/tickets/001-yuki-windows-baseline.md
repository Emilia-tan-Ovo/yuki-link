# Ticket 001：建立 Yuki Windows 可复现源码基线

状态：建议，未实施。先确认本 ticket 的实施方案，再进行源码引入和新环境验证。

## 问题

现有启动入口依赖 uv cache 中的 Windows-MCP 0.8.5 环境；本次未找到独立的自定义源码仓库。直接在缓存里继续开发，会使改动追踪、重建环境和后续接入难以维护。

## 目标

确认 Yuki Windows 的定制究竟位于源码还是接入配置，并为后续 computer provider 建立一份来源明确、可重建的基线。现有运行链路保留原位。

## 范围

1. 根据盘点位置核验上游 0.8.5 的确切来源、许可证和文件基线，补充本地安装记录之外的独立证据。
2. 在不读取凭证的前提下确认非敏感启动需求、公开工具范围与定制点；如确需查看敏感配置，先单独说明必要字段并取得授权。
3. 决定采用固定版本依赖还是维护 fork；只有真实源码差异或扩展需求证明有必要时才引入 fork。
4. 在项目内记录必要的来源、版本和校验信息；只引入选定方案需要的源码/许可证或依赖声明，不复制整个 uv 环境、设备标识、日志和真实配置。
5. 选定语言与依赖管理方式后，在隔离的新环境验证可重建性。验证不替换当前启动脚本或隧道。

## 验收

- 清楚区分上游源码、已确认的本地定制与外部插件；未知项明确列出。
- 有来源/版本/校验记录和可重复的环境构建步骤；在新环境验证导入及工具清单，不触发桌面操作。
- 原有安装代码、启动入口和配置未改动；用校验和证明涉及的旧源码保持原状。
- 仓库不含凭证、个人设备身份、运行日志或真实隧道配置。
- 形成一个简短且可执行的后续接入决定。

## 不在本 ticket 内

替换现有服务、修改隧道、发布远程服务、集成手机、实现叫车/点餐/支付、将外部 Commander 插件当成本项目源码。
