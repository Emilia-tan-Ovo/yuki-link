# 仓库结构建议

当前只确定模块职责和目录，不创建运行时实现，也不预先决定语言、框架、进程数量、数据库或部署平台。

## 统一核心

- `core/mcp`：面向调用方的 MCP 入口，负责协议输入输出与能力发布。
- `core/bridge`：统一发现 provider、选择实现、执行调用及整理结果；后续在这里落实授权上下文、超时、取消与错误分类。
- `core/contracts`：核心、能力模块和 adapter 共同遵循的最小 Interface；按首个真实接入需要逐步定义，避免提前设计一个万能命令系统。

Bridge 是逻辑上的协调核心，不意味着本轮已经决定另建网络服务。能力的业务规则归各能力模块，第三方 SDK、设备连接和上游 MCP 协议细节归 adapter。

## 按能力组织服务

`capabilities/alarm`、`ride`、`food`、`expense` 各自容纳能力定义、业务规则与必要的服务编排。实现代码出现后再细分内部文件，不提前建立多层空包。

例如：闹钟可能由手机系统、桌面提醒或外部日程服务提供；记账可能通过本地数据或远程服务完成；打车和点餐也可能使用服务接口或手机操作。它们均不归属于 `providers/phone`。

## provider 与 adapter

- `providers/computer/yuki-windows`：未来包装既有 Windows 接入；本轮未复制、修改或接管它。
- `providers/phone/community-mobile-mcp`：未来社区 mobile MCP 接入位置；尚未选定具体项目、版本或兼容方案。
- `providers/services`：非设备专属的服务接入；首次真实接入时再创建具体子目录。

Provider 是提供能力的接入方，Adapter 是把其实现适配到核心 Interface 的代码。二者不是需要另建两套平行目录的概念。

依赖方向：MCP 入口调用 Bridge；Bridge 调度能力流程；能力流程通过契约请求 provider。核心和能力模块不直接依赖具体 Windows/手机 SDK；具体 provider 实现契约，由未来启动装配入口注册。provider 不相互调用。

社区 mobile MCP 可作为外部进程/服务由 adapter 调用；是否采用该方式需在后续 ticket 结合项目许可证、协议、能力和运行限制确认。不能假定任意社区 MCP 已经支持 alarm/ride/food/expense 的业务语义。

## 首次实现时要落实的行为

- 能力发现明确设备、provider 与支持范围；不支持、离线、未授权和执行失败分别返回。
- 根据用户目标选择已注册 provider，不默默切换设备或服务完成有副作用的操作。
- 对订餐、叫车等操作区分准备与提交；提交需匹配实际授权，超时不能盲目重试下单。
- 返回可追踪的操作结果；日志只记录必要且脱敏的元数据。
- 通过公开 Interface 验证行为：fake provider 覆盖离线、失败与不支持，再增加真实只读接入测试。

这些是设计方向，并非骨架已经实现的功能。已有 Windows-MCP 是现成依赖，不把其每个工具机械包装成新的同名空层；先用一个真实、只读的用例确定需要隐藏的连接与错误处理复杂度。
